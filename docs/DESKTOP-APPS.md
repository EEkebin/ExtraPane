# ExtraPane app (0.13)

Run **ExtraPane.exe** on either PC. Choose **Server** in the left sidebar on the PC being extended, and **Client** on the receiving PC. **About** is at the bottom. One portable ZIP and one per-user installer include both roles, and page changes preserve each role's state. Close hides the single app to the tray; tray Exit shuts down both roles.

The main app runs without elevation. Start Driver requests administrator approval for its fixed-purpose helper, which owns the engine/firewall and communicates over a user-restricted named pipe with process-identity checks. The app no longer needs saved pairing credentials. Server mode requires the development display driver, installed by choosing Server + Client in Setup or by running the bundled driver installer for a portable host. Receiving does not require that driver. See [driver installation](DRIVER-INSTALLATION.md).


## Normal sessions

Debug is unchecked on every app launch. After a valid client connection, the host creates a real extended Windows desktop using the client screen as the resolution/refresh preference (3000x2000/60 on the Surface Book 2). No four-color test window is launched. Move an application onto the extra monitor and use the laptop normally. A blank desktop background before you move a window there is expected.

There is no frame count or elapsed-session limit. Disconnect from Client or close the receiver preview with **F9** to end reception. The server removes that client?s monitor and keeps listening. Windows allocates independent client monitors dynamically, subject to OS and hardware availability. **Stop Driver** removes all session monitors. Closing either setup window hides it to the tray; Open restores it and Exit shuts it down. Launching the same role again restores its existing setup window. **F8** pauses/resumes receiver input. Connection loss, a frozen peer, unrecoverable GPU loss or deliberate display removal still end a session and release held input. Continuous does not mean automatic reconnection across sleep, Wi-Fi loss or reboot; click Connect again after a disconnect. Restart the driver after local adapter/address changes.

The Server Debug checkbox limits a session to 3,600 frames and opens a 60-second color/motion/input diagnostic window. Debug on either endpoint displays connection details in that app. Debug is a runtime option independent of Release/Debug compiler configuration.

## Automatic LAN connections

Start Driver accepts reachable clients automatically, without pairing or approval. Each client enters only the server address. TLS encrypts traffic but does not verify peer identity. The Server input checkbox grants remote control to connected clients; use automatic mode on a trusted LAN.

Both apps list IPv4/IPv6 addresses and names of connected physical adapters automatically. Only Client has a Server address field. Transport currently uses IPv4: Server listens on active local IPv4 addresses and Windows selects the client source interface through its route to the server. Settings persist under `HKCU\Software\DM\Host` or `Receiver`. DHCP is not required; reachable static Ethernet addresses use the same path. There is no discovery service.

Start Driver on the elevated server creates a Windows Firewall rule scoped to the engine executable, active non-loopback local IPv4 addresses and TCP port 43824. Remote scope includes LocalSubnet, private IPv4, link-local and shared-address ranges, supporting routed LANs without entering a client address. Connections use automatic TLS with no saved pairing. Stop Driver or tray Exit removes the rule. If the UI crashes, the engine stops when its launcher exits; the narrowly scoped rule may remain until the next Start/Stop Driver. An existing rule pointing to a different executable is not overwritten. The receiver initiates an outbound connection and needs no inbound rule.

Input remains explicitly controlled by each app's mouse/keyboard/touch/pen checkbox. Neither audio nor mic passthrough is implemented yet. No SSH password field exists. `scripts/deploy_test_apps.py` is development deployment/testing infrastructure, not a runtime dependency or part of the distributed app folder.

## Implementation and protocol

The current launchers use native C++/WinRT and WinUI 3 controls, with XAML loaded through XamlReader and an explicit WinUI metadata provider. The D3D11 preview keeps a native window and a small local overlay. The previous Win32 setup windows remain developer diagnostics. UI actions launch a hidden engine process and consume bounded status output; no pixels or pen samples go through UI text controls. Per-user settings exclude secrets. Controls scale with system DPI and fullscreen preview retains per-monitor DPI awareness.

Protocol version 7 retains `Offer.frames == 0` as continuous. Both endpoints must be updated; old offers/requests are rejected. Pixel, payload, input-batch, capability and authentication bounds remain enforced. Media timestamps and counters use 64-bit frame indices; the 32-bit wire sequence wraps explicitly. Default `dm-view host` is continuous; `--frames N` opts into a bounded diagnostic. `--timeout-ms 0` on the host waits for a receiver without an accept timeout. Network-operation and input-watchdog deadlines remain active.

The engine monitors its launcher's process lifetime. Stop Driver or tray Exit terminates the owned server engine; the separate input watchdog observes pipe closure and releases contacts. No kill-on-close job includes the input watchdog. After its first authenticated client connects, the virtual monitor belongs to the running server engine and survives client disconnects, rejected authentication and later connections. It disappears when that engine ends. Host display setup reads actual pixels with per-monitor DPI awareness, places DM to the right of the physical layout and restores physical origins if Windows moves them during virtual-monitor arrival. It does not change physical resolutions or refresh rates.

## Display Settings changes (0.9)

While connected, open Windows Settings > System > Display on the host. Select DM LAN Display, drag it into position, or change its resolution/orientation and click Apply/Keep changes. The session retains the same virtual monitor and encrypted connection while rebuilding capture, encoding and decoding for the actual Windows mode. Expect a brief frozen/black image during recovery. It does not reset Windows to the startup resolution on every change. Recovery waits up to 20 seconds for the selected display to stabilize; network loss and unsupported modes can still end a session.

The host launcher remembers the resulting resolution, refresh, rotation and position under `HKCU\Software\DM\Display`. Restarting with the same client screen resolution restores that layout. Connecting from a client with a different screen resolution chooses a new starting profile. CLI users opt into this with `--keep-layout`. Only the most recent layout is retained, not separate layouts for multiple receivers.

Portrait video preserves its aspect ratio with black bars. Mouse, touch and pen map to the visible image; new pointer contacts in the bars are ignored. Held input is released during geometry changes, queued samples are discarded, and a fresh input epoch prevents stale replay. Native pointer injection accounts for negative virtual desktop origins.

Protocol v6 reserves a zero-payload frame header for a replacement offer and decoder-ready acknowledgement. Both endpoints must be updated together. The separately installed 0.7 display driver is unchanged. These changes do not add sleep/network reconnection or support disabling/cloning the DM monitor.

WinUI 3 and portable Client/Server folders are implemented in 0.10. The virtual-display driver still needs separate installation/signing; the ZIPs never modify driver-signing or security policy.

Validation on 2026-11-02: Release and Debug each pass all five suites. Continuous local sessions survived six changes covering every orientation, negative placement, 720p and 1080p, with the same monitor identity; restarting restored portrait geometry and placement. The native portrait test verified mouse/key/two-contact touch, pressure/tilt/rotation/barrel/eraser/inversion, watchdog cleanup and held key/button release after movement. Independent TLS input rejection checks pass with protocol v6. On the Surface Book 2, one 7,200-frame session survived four live changes, decoded every frame on the Intel GPU, and delivered generated mouse/key/two-contact touch/pen (pressure 897) after portrait recovery. Physical pen/touch acceptance through manually applied Settings changes remains a user check. Evidence: `out/display-reconfigure-test.json` and `out/laptop-reconfigure-test.json`.

## Client-driven mode and local window controls (0.10)

Before receiving video, the client reports the pixel dimensions and refresh of the monitor containing its preview. The nominal 59.94 Hz panel mode is targeted at 60 fps. The server selects the closest advertised DM driver mode within the H264 limits (4096 per axis, 8,847,360 pixels, even dimensions, 60 fps). Exact matching wins; otherwise aspect ratio, pixel area and refresh determine the fallback. The Server shows the client request and selected mode. Portrait clients can select rotated modes. Windows Settings overrides made afterward take precedence and are remembered for the same client resolution profile. Changing the client window size does not change the extended monitor resolution; it scales and letterboxes the image. A new connection renegotiates the client's monitor preferences.

The preview starts windowed with normal resizable borders and title-bar controls. Its additional toolbar offers Minimize, Maximize/Restore, Fullscreen/Windowed and Close. It hides after 2.5 seconds away from the toolbar. Hover the mouse for 600 ms in the centered 96-by-8 logical-pixel strip, or swipe down at least 24 logical pixels starting in that strip, to reveal it. Pen input never activates this gesture; other top-edge taps go to the remote app. F10 reveals the bar, F11 toggles fullscreen, F8 pauses input, Ctrl+Shift+Q disconnects, F9 also closes. Fullscreen exit restores the prior window placement. Toolbar and reserved shortcut actions stay local and release remote held input. Only the small top-center touch strip is reserved for local controls. The disconnect shortcut is registered while the preview is open; if another app owns it, it still works while the preview has focus.

Protocol 7 extends the authenticated client request to 32 bytes with bounded width/height/refresh preferences. `dm-view host --client-mode --extend` enables this policy; explicit CLI resolution tests can still select their own profile. Both endpoints need the same protocol. Automatic reconnect and dynamic renegotiation when dragging the client window to another physical monitor remain future work.

## Portable bundles

`./scripts/build-apps.ps1` builds the engine and MSBuild WinUI projects; `python scripts/package_apps.py` creates `out/dist/ExtraPane-0.13.0-win-x64.zip` and SHA256SUMS.txt. NuGet packages are pinned by packages.lock.json. The shell uses Windows App SDK 1.8.260921001 and C++/WinRT 2.0.250303.1, with the self-contained runtime and hybrid CRT; the engine keeps its static CRT. See [Microsoft's self-contained deployment guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps).

Extract the entire folder and run ExtraPane.exe. Runtime DLLs, resources, dependency licenses, a file hash manifest and README travel together. No pairing key, address setting, SSH tool, test snapshot, log or private certificate is bundled. Pairing/settings remain per-user on the computer. Portable hosts run the included ExtraPane.DriverSetup.exe before hosting. The current driver is development signed; setup asks for certificate consent and elevation. Per-user app setup and a separate machine-wide driver uninstaller are implemented. Production signing and ARM64 packages remain future work. See DRIVER-INSTALLATION.md for current deployment behavior.

## Persistent driver and tray (0.11)

`dm-view host --serve --extend --client-mode --keep-layout --bind auto --name dm-lan --allow-screen` is the normal Server engine mode. Start Driver starts the listener without creating a monitor. Only an authenticated, validated client request creates the first virtual monitor using client preferences (or the matching saved Windows layout). That monitor then remains present between client sessions. Windows layout changes made while disconnected are preserved when the same client profile returns. Stop/Exit saves the current layout before removing the monitor. Only one client connects at a time.

## Connection quality and optional statistics

The client floating toolbar has a Settings menu. Statistics are hidden by default and enabled with **Show statistics**; the main setup window has no permanent quality panel. The dark, click-through overlay shows received and presented FPS, target FPS, actual encoded-video Mbps, stream dimensions, cumulative preview frames skipped, average decode time, and render/present time. Render time includes presentation/vsync waits. These are local pipeline measurements, not end-to-end latency or packet-loss estimates. A static desktop can have a very low bitrate while still receiving 60 frames per second.

Native resolution is the default. Optional 75% and 50% stream scales are fixed for each connection and saved in `HKCU\Software\DM\Receiver\StreamScale`. They apply after disconnect/reconnect. The old Quality preference is ignored so an upgrade starts with the native baseline. Target FPS is unchanged (up to 60), and scaling never changes Windows monitor geometry.

Protocol 9 removes the per-frame quality feedback and adaptive codec rebuilds. Input still returns before decoding, as in pre.14; video-only sessions no longer wait for a receiver report before sending the next frame. Actual Windows display changes still rebuild the pipeline and renew input epochs safely. Both PCs must be updated.

Validation includes original pre.14 and pre.21 release-engine comparisons on the same local GPU/capture workload, fixed-profile TLS/H264 tests with stalled receivers and no feedback, input protocol/watchdog tests, and four simultaneous extended streams. Local tests are not an end-to-end Surface/Wi-Fi latency measurement.
