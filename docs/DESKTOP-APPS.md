# SideScreen Client and Server (0.11)

Open **SideScreen Server** on the desktop and click **Start Driver**. Open **SideScreen Client** on the laptop, enter a server IPv4 address, then click **Connect**. Installed shortcuts point to `%LOCALAPPDATA%\DM\Server\Server.exe` and `%LOCALAPPDATA%\DM\Client\Client.exe`. Extracted portable folders work without app installation. Normal use does not involve SSH, Python or PowerShell. Server elevation and the separately installed 0.7 virtual-display driver are still required; Client runs as the normal signed-in user.

## Normal sessions

Debug is unchecked on every app launch. The host creates a real extended Windows desktop using the client screen as the resolution/refresh preference (3000x2000/60 on the Surface Book 2). No four-color test window is launched. Move an application onto the extra monitor and use the laptop normally. A blank desktop background before you move a window there is expected.

There is no frame count or elapsed-session limit. Disconnect from Client or close the receiver preview with **F9** to end reception. The server keeps its monitor and listens for the next client. **Stop Driver** removes the monitor. Closing either setup window hides it to the tray; Open restores it and Exit shuts it down. Launching the same role again restores its existing setup window. **F8** pauses/resumes receiver input. Connection loss, a frozen peer, unrecoverable GPU loss or deliberate display removal still end a session and release held input. Continuous does not mean automatic reconnection across sleep, Wi-Fi loss or reboot; click Connect again after a disconnect. Restart the driver after local adapter/address changes.

The Server Debug checkbox limits a session to 3,600 frames and opens a 60-second color/motion/input diagnostic window. Debug on either endpoint displays connection details in that app. Debug is a runtime option independent of Release/Debug compiler configuration.

## Pairing and LAN settings

The two authorized test computers are provisioned with the same random 256-bit `dm-lan` pairing key, retained in each user's Windows Credential Manager. The key is never stored in Git, settings, logs or process arguments. For another setup, generate a code in either app, copy it to the other app, and click Save pairing on both. Copy before saving because Save clears the field. Forget pairing explicitly revokes the local credential; an existing pairing is never silently overwritten.

Both apps list local IPv4/IPv6 addresses and adapter names automatically. Only Client has a Server address field. Transport currently uses IPv4: Server listens on active local IPv4 addresses and Windows selects the client source interface through its route to the server. Settings persist under `HKCU\Software\DM\Host` or `Receiver`. DHCP is not required; reachable static Ethernet addresses use the same path. There is no discovery service.

Start Driver on the elevated server creates a Windows Firewall rule scoped to the engine executable, active non-loopback local IPv4 addresses and TCP port 43824. Remote scope includes LocalSubnet, private IPv4, link-local and shared-address ranges, supporting routed LANs without entering a client address. Pairing authentication is mandatory. Stop Driver or tray Exit removes the rule. If the UI crashes, the engine stops when its launcher exits; the narrowly scoped rule may remain until the next Start/Stop Driver. An existing rule pointing to a different executable is not overwritten. The receiver initiates an outbound connection and needs no inbound rule.

Input remains explicitly controlled by each app's mouse/keyboard/touch/pen checkbox. Neither audio nor mic passthrough is implemented yet. No SSH password field exists. `scripts/deploy_test_apps.py` is development deployment/testing infrastructure, not a runtime dependency or part of the distributed app folder.

## Implementation and protocol

The current launchers use native C++/WinRT and WinUI 3 controls, with XAML loaded through XamlReader and an explicit WinUI metadata provider. The D3D11 preview keeps a native window and a small local overlay. The previous Win32 setup windows remain developer diagnostics. UI actions launch a hidden engine process and consume bounded status output; no pixels or pen samples go through UI text controls. Per-user settings exclude secrets. Controls scale with system DPI and fullscreen preview retains per-monitor DPI awareness.

Protocol version 7 retains `Offer.frames == 0` as continuous. Both endpoints must be updated; old offers/requests are rejected. Pixel, payload, input-batch, capability and authentication bounds remain enforced. Media timestamps and counters use 64-bit frame indices; the 32-bit wire sequence wraps explicitly. Default `dm-view host` is continuous; `--frames N` opts into a bounded diagnostic. `--timeout-ms 0` on the host waits for a receiver without an accept timeout. Network-operation and input-watchdog deadlines remain active.

The engine monitors its launcher's process lifetime. Stop Driver or tray Exit terminates the owned server engine; the separate input watchdog observes pipe closure and releases contacts. No kill-on-close job includes the input watchdog. The virtual monitor belongs to the running server engine and survives client disconnects, rejected authentication and later connections. It disappears when that engine ends. Host display setup reads actual pixels with per-monitor DPI awareness, places DM to the right of the physical layout and restores physical origins if Windows moves them during virtual-monitor arrival. It does not change physical resolutions or refresh rates.

## Display Settings changes (0.9)

While connected, open Windows Settings > System > Display on the host. Select DM LAN Display, drag it into position, or change its resolution/orientation and click Apply/Keep changes. The session retains the same virtual monitor and encrypted connection while rebuilding capture, encoding and decoding for the actual Windows mode. Expect a brief frozen/black image during recovery. It does not reset Windows to the startup resolution on every change. Recovery waits up to 20 seconds for the selected display to stabilize; network loss and unsupported modes can still end a session.

The host launcher remembers the resulting resolution, refresh, rotation and position under `HKCU\Software\DM\Display`. Restarting with the same client screen resolution restores that layout. Connecting from a client with a different screen resolution chooses a new starting profile. CLI users opt into this with `--keep-layout`. Only the most recent layout is retained, not separate layouts for multiple receivers.

Portrait video preserves its aspect ratio with black bars. Mouse, touch and pen map to the visible image; new pointer contacts in the bars are ignored. Held input is released during geometry changes, queued samples are discarded, and a fresh input epoch prevents stale replay. Native pointer injection accounts for negative virtual desktop origins.

Protocol v6 reserves a zero-payload frame header for a replacement offer and decoder-ready acknowledgement. Both endpoints must be updated together. The separately installed 0.7 display driver is unchanged. These changes do not add sleep/network reconnection or support disabling/cloning the DM monitor.

WinUI 3 and portable Client/Server folders are implemented in 0.10. The virtual-display driver still needs separate installation/signing; the ZIPs never modify driver-signing or security policy.

Validation on 2026-11-02: Release and Debug each pass all five suites. Continuous local sessions survived six changes covering every orientation, negative placement, 720p and 1080p, with the same monitor identity; restarting restored portrait geometry and placement. The native portrait test verified mouse/key/two-contact touch, pressure/tilt/rotation/barrel/eraser/inversion, watchdog cleanup and held key/button release after movement. Independent TLS input rejection checks pass with protocol v6. On the Surface Book 2, one 7,200-frame session survived four live changes, decoded every frame on the Intel GPU, and delivered generated mouse/key/two-contact touch/pen (pressure 897) after portrait recovery. Physical pen/touch acceptance through manually applied Settings changes remains a user check. Evidence: `out/display-reconfigure-test.json` and `out/laptop-reconfigure-test.json`.

## Client-driven mode and local window controls (0.10)

Before receiving video, the client reports the pixel dimensions and refresh of the monitor containing its preview. The nominal 59.94 Hz panel mode is targeted at 60 fps. The server selects the closest advertised DM driver mode within the H264 limits (4096 per axis, 8,847,360 pixels, even dimensions, 60 fps). Exact matching wins; otherwise aspect ratio, pixel area and refresh determine the fallback. The Server shows the client request and selected mode. Portrait clients can select rotated modes. Windows Settings overrides made afterward take precedence and are remembered for the same client resolution profile. Changing the client window size does not change the extended monitor resolution; it scales and letterboxes the image. A new connection renegotiates the client's monitor preferences.

The preview starts windowed with normal resizable borders and title-bar controls. Its additional toolbar offers Minimize, Maximize/Restore, Fullscreen/Windowed and Close. It hides after 2.5 seconds away from the toolbar. Move the mouse to the top edge, or touch/drag down from the top 24 logical pixels, to reveal it. F10 reveals the bar, F11 toggles fullscreen, F8 pauses input, F9 closes. Fullscreen exit restores the prior window placement. Toolbar and reserved shortcut actions stay local and release remote held input. The top-edge touch reveal area is reserved for local controls.

Protocol 7 extends the authenticated client request to 32 bytes with bounded width/height/refresh preferences. `dm-view host --client-mode --extend` enables this policy; explicit CLI resolution tests can still select their own profile. Both endpoints need the same protocol. Automatic reconnect and dynamic renegotiation when dragging the client window to another physical monitor remain future work.

## Portable bundles

`./scripts/build-apps.ps1` builds the engine and MSBuild WinUI projects; `python scripts/package_apps.py` creates `out/dist/SideScreen-0.11.0-{Client,Server}-win-x64.zip` and SHA256SUMS.txt. NuGet packages are pinned by packages.lock.json. The shell uses Windows App SDK 1.8.260921001 and C++/WinRT 2.0.250303.1, with the self-contained runtime and hybrid CRT; the engine keeps its static CRT. See [Microsoft's self-contained deployment guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps).

Extract the entire folder and run Client.exe or Server.exe. Runtime DLLs, resources, dependency licenses, a file hash manifest and README travel together. No pairing key, address setting, SSH tool, test snapshot, log or private certificate is bundled. Pairing/settings remain per-user on the computer. Server ZIPs require an already installed compatible driver and elevation. The current driver is a development test-signed component; production Authenticode signing, driver distribution, installer/update support and ARM64 packages remain release work.

Validation for 0.10: both actual WinUI content trees render and pass initial-state checks, including the extracted laptop Client. Release/Debug each pass five suites. The preview test passed resize, fullscreen monitor bounds, window placement restoration, maximize/restore, minimize, toolbar hide and mouse/keyboard reveal while streaming. Six host Display Settings changes and saved-layout restart passed again; protocol 7 permission/epoch/sequence/bounds rejection checks passed. The extracted Server and Client connected through their normal UI actions: Surface Book native 3000x2000/60 was selected with no fallback, and generated mouse/key/two-contact touch/pen pressure 897 reached the host after window-control tests. Timed test-only app shutdown released the session and restored the physical monitors. Evidence: out/portable-laptop-test.json. Real finger top-edge gestures and subjective toolbar appearance still need user acceptance; the native Computer Use helper was unavailable. WinUI render artifacts were inspected directly.

## Persistent driver and tray (0.11)

`dm-view host --serve --extend --client-mode --keep-layout --bind auto --name dm-lan --allow-screen` is the normal Server engine mode. One virtual monitor remains present before and between client sessions. The last saved profile is restored at startup; the first connection chooses client preferences when no matching profile exists. Windows layout changes made while disconnected are preserved when the same client profile returns. Stop/Exit saves the current layout before removing the monitor. Only one client connects at a time.

Validation: Release and Debug pass all five suites. The persistent-driver test rejects an incorrect pairing, survives disconnect, preserves monitor identity and portrait placement across reconnect (including an offline move), and restores the exact physical baseline on stop. Two bounded completed sessions also relisten successfully. Native tray tests verify hide/reopen, Start/Stop Driver and true Exit cleanup. Evidence: `out/driver-service-test.json` and `out/driver-bounded-test.json`.

The 0.11 extracted packages passed the Surface Book 2 GUI session: native 3000x2000/60 preference without fallback, resize/fullscreen/maximize/minimize/toolbar controls, tray hide/reopen, and generated mouse/key/two-touch/pen delivery (pressure 897). Server resumed listening after Client exited. Timed shutdown restored the two physical monitors. The test cleanup initially reported an absent firewall rule as a PowerShell failure after all assertions passed; cleanup now treats an already-removed rule as success. Evidence: `out/portable-laptop-test.json`.
