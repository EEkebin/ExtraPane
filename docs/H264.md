# Hardware H264 preview

Version 0.4 now keeps H264 raw pixels on the GPU; see GPU.md for the current pipeline and results. The CPU-bridge timings below preserve the earlier 0.3 baseline for comparison.

The default `dm-view` codec is now hardware H264. On 2026-11-01 it streamed 1280x720 at 30 fps from the NVIDIA desktop to the Windows laptop. The longer test decoded every one of 300 access units and presented 297 frames in the native preview. The three skipped presentations reflect the bounded latest-frame queue; they were not lost network packets.

This is a working codec/transport feasibility slice, not the finished 1080p60 display product. Input, audio, pen, virtual display/microphone endpoints, and Windows+K remain separate work.

## Actual codec selection

- Encoder: **NVIDIA H.264 Encoder MFT**, selected exclusively from Media Foundation's hardware encoder category. Asynchronous input/output events are handled with bounded waits. Low-latency mode is required; B-picture count zero, a one-second GOP, Main profile, and a 4 Mbps target are configured where supported. Failure to activate/configure a hardware encoder is an error, not a hidden software fallback.
- Decoder: **Microsoft H264 Decoder MFT** with an **Intel UHD Graphics 620** D3D11 device on the laptop. It receives a DXGI device manager, requires D3D11 awareness, and must return NV12 textures through `IMFDXGIBuffer`. Plain memory output is rejected. Maximum coded dimensions are constrained before streaming, and output geometry is checked again before copying pixels.
- The standalone `codec-check` encodes and decodes 16 changing-color frames. It checks frame count, color, order, and GPU-surface output. Both Debug and Release passed on the desktop. Merely enumerating a codec registration is not used as proof.

Implementation follows [asynchronous MFT processing](https://learn.microsoft.com/en-us/windows/win32/medfound/asynchronous-mfts), [low-latency codec behavior](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avlowlatencymode), and [D3D11 media decoding](https://learn.microsoft.com/en-us/windows/win32/medfound/supporting-direct3d-11-video-decoding-in-media-foundation). The similarly named [AVDecVideoAcceleration_H264 property](https://learn.microsoft.com/en-us/windows/win32/codecapi/avdecvideoacceleration-h264-property) does not enable acceleration for an MFT; the D3D11 device-manager integration supplies that path.

## Current path and remaining copies

The initial 0.3 path read the desktop texture into CPU memory, scaled through WIC, and converted pixels to NV12 on CPU. Decode yielded NV12 GPU surfaces, then read them back and converted/uploaded BGRA for presentation. This is the historical baseline, replaced by the GPU path in 0.4.

The current 0.4 path removes those raw-pixel CPU bridges. GPU-to-GPU copies and compressed CPU/TLS buffers remain, so this is not a literal zero-copy pipeline. Glass-to-glass latency has not been measured. A four-Mbps target does not guarantee a network rate or constant quality.

## Running

Provision a random pairing using `dm-session` as described in SECURITY.md. On the host:

```powershell
.\dm-view.exe host --name PAIR_NAME --bind HOST_IP --allow-screen --frames 180 --fps 30 --timeout-ms 60000
```

On the receiver:

```powershell
.\dm-view.exe receive --name PAIR_NAME --bind RECEIVER_IP --peer HOST_IP
```

Default TCP port: 43824. Default codec: `h264`. Select `--codec jpeg` explicitly for the earlier diagnostic path. Both endpoints must use video protocol version 3. The receiver acknowledges decoder readiness before the host starts streaming, preventing frames from accumulating during GPU initialization. The offer identifies the codec; unknown versions, codecs, grants, odd H264 dimensions, oversized payloads, and invalid frame ordering are rejected.

The view-only permission boundary is unchanged: the host must pass `--allow-screen`, TLS must authenticate, and the receiver must send the supported video request before capture opens. No keyboard, pointer, audio, or microphone permissions are added.

## Surface Book 2 and hybrid GPU selection

The user identified the reference receiver as a Surface Book 2 with GTX 1050. Live DXGI inspection confirmed both physical GPUs: adapter 0 is Intel UHD 620 with one attached desktop output; adapter 1 is NVIDIA GeForce GTX 1050 with approximately 2 GiB dedicated memory and no directly attached desktop output. Both report a supported NV12/H264 720p decoder configuration. The NVIDIA encoder registration is therefore consistent with actual installed hardware, not evidence of a stale entry.

`dm-view info` inventories hardware adapters, attached outputs, and 720p decode configurations. Default decoder selection remains Windows' default hardware adapter. Override with `--decoder-adapter INDEX`; zero is valid. An unavailable/software adapter is rejected. In 0.3 the renderer was independent; in 0.4 the H264 preview shares the decoder's GPU device to avoid raw-pixel uploads. Both names are logged. JPEG remains on its earlier path.

Example diagnostic override on this laptop:

```powershell
.\dm-view.exe receive --name PAIR_NAME --bind RECEIVER_IP --peer HOST_IP --decoder-adapter 1
```

Adapter indices are diagnostic enumeration indices, not persistent device identifiers; inventory them again after topology changes. Selecting the GTX 1050 for decode does not automatically improve presentation latency or battery use. On this laptop the Intel GPU owns the panel, and moving work between GPUs may add transfers. Keep the default path until controlled end-to-end and power measurements justify a different policy. This matches [Microsoft's hybrid graphics model](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/using-cross-adapter-resources-in-a-hybrid-system). A detached/missing selected GPU currently terminates the session; automatic migration is not implemented.

Explicit GTX 1050 testing also passed: 300 decoded GPU-surface frames, 297 presented frames, and a 10.030-second host run. The preview renderer identified itself separately as Intel UHD 620. Average decoder/readback/conversion work was 19.458 ms/frame in that run. Both laptop GPUs are therefore usable; these individual runs do not establish a performance or battery-life winner. Default Intel selection remains unchanged and no system-wide graphics preferences were modified.

The first GTX run exposed a startup backlog while its decoder device was created. Protocol version 3 adds the ready acknowledgement and refreshes the first captured frame after it; the host no longer streams into an uninitialized receiver. In the repeated GTX run, the receiver's timed stream duration matched the host's approximately ten seconds instead of starting partway through a queued burst.

Hardware check and interruption check:

```powershell
.\dm-view.exe codec-check
python .\scripts\test_video_recovery.py
```

Use `scripts/test_video_laptop.py --laptop-ip ... --desktop-ip ... --user ... --frames 300 --fps 30` for the two-device run. This still uses disposable Credential Manager pairings, temporary per-peer/program/port firewall rules, and an interactive desktop task launched over SSH. Cleanup removes the pairings, firewall rules, task, and key-free helper script. Executables remain in the user's local app-data test directory.

These are single-run stage averages, not p95 latency, end-to-end latency, sustained performance guarantees, or directly comparable quality measurements against the earlier JPEG capture. Stage timings cover CPU bridges as described above. Receiver decoder identity includes the actual adapter name in the log. Structured reports are under ignored `out/laptop-h264-test.json`, `out/laptop-h264-adapter-1-test.json`, `out/laptop-gpu-inventory.json`, and `out/video-recovery-test.json`.

Interruption testing used process loss over loopback, not physical cable loss or silent packet loss. Recovery currently means starting a fresh session; automatic reconnect and active-session revocation remain unimplemented. The four default CTest suites continue to cover portable protocol validation, network behavior, TLS rejection/revocation, and JPEG/protocol bounds without requiring an active desktop or hardware encoder.
