# D3D12 client renderer

Choose the renderer in the main app's **Settings > Client > Renderer** before connecting. D3D11 remains the default. Renderer selection is saved under the existing per-user Receiver settings and cleared by the uninstaller's remove-settings option. The selector is locked during a client session. There is no live renderer switching in the preview toolbar.

The same Settings page groups client input/debug options and server input/debug options. Each role locks its own controls while running; switching pages leaves sessions alone. Statistics and one-shot stream-resolution choices stay in the receiving preview's Settings menu.

## Pipeline and support

Server capture and H.264 encoding remain unchanged. The client still decodes into owned D3D11 NV12 textures. D3D12 uses the same GPU adapter, copies into a shared NV12 GPU texture, waits on a shared D3D11/D3D12 fence, converts color and scales with a native D3D12 pixel shader, then presents through a D3D12 swapchain. The input remains in COMMON state when handed between APIs. Completion is bounded to one GPU frame in flight. Production does not read pixels back to CPU memory or upload decoded pixels from it.

The support probe creates a D3D12 device, graphics pipeline, shared NV12 texture and shared fences against the default decoder adapter. It checks execution of cross-API synchronization, not just DLL availability. Unsupported options remain visible and disabled with a yellow reason. The actual stream dimensions/device are checked again on connection and reconfiguration. A D3D12 failure reports its reason and falls back to D3D11; underlying decoder/device failures can still end a session.

This renderer is independent of the wire codec and server renderer. Protocol 9 is unchanged. D3D12 does not guarantee higher frame rate or lower end-to-end latency. The shared-texture copy and synchronization are real costs; no comparative latency or battery improvement is claimed.

Microsoft references: [shared handles and D3D11/D3D12 interoperability](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createsharedhandle), [explicit synchronization responsibilities](https://learn.microsoft.com/en-us/windows/win32/direct3d12/porting-from-direct3d-11-to-direct3d-12).

## Validation

- RTX 4090, Intel UHD 620 and GTX 1050 passed GPU pixel validation for NV12 color, orientation, padded-surface crop, aspect-fit letterboxing, texture resize and shared fences. The diagnostic enables the D3D12 debug layer when installed and rejects validation errors.
- Native 3000x2000 Surface runs decoded 360 frames each at approximately 60 received FPS: 354 presented on Intel and 349 on GTX, including startup. Both used D3D12 with zero application raw-pixel readbacks/uploads. These short runs used a mostly static desktop and are functional checks, not latency benchmarks.
- Window resize, fullscreen/restore, maximize/minimize, statistics, toolbar gestures and disconnect passed with D3D12 active.
- Live host resolution, portrait/inverted rotation and negative placement changes preserved the session; saved portrait geometry survived reconnect.
- Shared Settings passed selection persistence across app restart, active-session locking, independent role options and ordinary close. An isolated synthetic unsupported-device report verified a visible disabled D3D12 choice, specific explanation, and saved-preference fallback. This fixture tests UI handling, not a physical unsupported GPU.

Manual hardware checks (require an idle interactive desktop and, for session tests, the already installed driver):

```powershell
out/build/windows-release/dm-view.exe renderer-info
out/build/windows-release/dm-view.exe d3d12-check
python scripts/test_renderer_preview.py --renderer d3d12
python scripts/test_display_reconfigure.py --renderer d3d12
powershell -File scripts/test_renderer_settings.ps1
powershell -File scripts/test_renderer_unavailable.ps1
```

The diagnostic readback/upload is restricted to `d3d12-check`. The unavailable-renderer fixture runs from an isolated disposable app copy. Test scripts do not install drivers. Human pen/touch and responsiveness acceptance remains the handoff before Vulkan, then OpenGL.
